## Deferred from: code review of story-2.1 (2026-08-18)

- **SQLite `lower()` is ASCII-only; production Postgres folds per database collation.** Layer B proves AC-3 only for ASCII pairs (`"API"`/`"api"`, `"Front"`/`"FRONT"`). `Component(name="ÉTUDE")` and `Component(name="étude")` collide on Postgres but both insert on SQLite — the one case where the two engines genuinely disagree is the case the suite cannot see. Needs a Postgres-backed run to close. [tests/test_components_models.py:390, 452-455]

- **`Component.save()` name normalization is a convention, not an invariant.** `bulk_create`, `QuerySet.update()`, `raw`, future data migrations, and `save(update_fields=[...])` omitting `"name"` all bypass the strip, so `"  API  "` and `"API"` can coexist in one project — the index is on `lower(name)`, not `lower(btrim(name))`, by design. Empty and whitespace-only names are likewise accepted at every layer (no `CHECK (length(btrim(name)) > 0)`). Out of 2.1's AC set: FR-6 maps to 2.2 and 3.1 (`docs/planning/epics.md:72`), which own serializer validation. Flagged so 2.2 does not assume the model layer already guarantees trimmed/non-empty. [addons/components/back/taiga_contrib_components/models.py:11, 17-20]

- **The `RunSQL` `lower(name)` index is invisible to Django's migration state.** `makemigrations --check --dry-run` compares model state and `RunSQL` contributes none, so renaming `Component.name`, adding `db_table`, or changing `max_length` would pass the drift check while silently breaking AC-3's index. Inherent to expressing the index as raw SQL (Django 3.2 cannot declare it); worth a comment in the migration at minimum. [addons/components/back/taiga_contrib_components/migrations/0001_initial.py:82-90]

- ~~**The addon package fence is a per-filename blacklist, not an allowlist.**~~ **Resolved in 2.2** — `tests/_addon_package.py` is the single `ALLOWED_STUB_APP_ENTRIES` source; `test_stub_app_importable_from_repo` and `test_package_file_allowlist` both import it. [tests/_addon_package.py]

- **Cross-project Assignment is not prevented at any layer — decide before 2.3 opens write paths.** The unique constraint is `(userstory, component)` only, so a UserStory in project A can be assigned a Component owned by project B: both FKs resolve, uniqueness is satisfied, the row persists. No AC in 2.1 covers it, and the project-scoped queries in 2.2/2.3/3.2/3.3 will all assume it cannot happen. [addons/components/back/taiga_contrib_components/models.py:33-41]

  **Why this is not "just validation, 2.3 owns it."** FR-6 trimming produces an ugly but meaningful row that a later serializer can normalize. This produces *incoherent* data, and no later layer can repair it — given a story in project A holding a component from project B, there is no correct answer to which project owns the truth. Rows admitted by the model layer are permanent. The cost is asymmetric: closing it now, against empty tables and an unreleased migration, is nearly free; closing it after 2.2/2.3 ship write paths costs a data migration *plus* a repair policy for whatever is already there.

  **Why it was not simply patched in 2.1.** No cheap airtight fix exists. A Postgres `CHECK` cannot span tables. A trigger means DDL the overlay exists to avoid (NFR-4). `Model.clean()` is bypassed by `bulk_create` / `QuerySet.update()` / raw SQL, i.e. the same non-invariant that already makes `Component.save()` stripping a convention rather than a guarantee.

  **Trap for whoever picks this up:** the obvious fix — denormalize `project_id` onto Assignment and add a composite constraint — is not obviously correct. Taiga supports moving a UserStory between projects; a denormalized `project_id` goes stale on that move, and the invariant becomes its own source of bugs. Any real fix has to state what happens to existing Assignments when a story changes project (cascade-delete them? re-point them? block the move?). That question is the actual decision, and it is a product question as much as a schema one.

## Deferred from: code review of story-2.2 (2026-08-18)

- **`name__iexact` and the `lower(name)` unique index fold differently, and the check is unlocked.** Django's `iexact` on Postgres compares via `UPPER()`, while the 2.1 index is on `lower(name)`. For locale-sensitive characters (Turkish dotted/dotless I under a `tr_*` collation, `ß`/`ẞ`) upper- and lower-folding are not inverses, so a name can pass `services.name_conflicts` and then violate the index — `IntegrityError` → 500, the exact failure AC-1 exists to prevent. Layer B cannot see it: SQLite `LIKE` is ASCII-only, so the harness proves case-insensitivity for ASCII only. Compounding it, `name_conflicts` is a bare `SELECT EXISTS` with no lock, so two concurrent POSTs of `"API"`/`"api"` both pass and the second 500s. Adjacent to the existing 2.1 deferred item on Postgres collation vs SQLite `lower()`; needs a Postgres stack to settle. [addons/components/back/taiga_contrib_components/services.py:12-19]

- **`normalize_name` is trim-only, so FR-6's intent is wider than its implementation.** `"Front End"` / `"Front  End"` / `"Front\tEnd"`, and NFC vs NFD spellings of the same accented name, all coexist in one project. Zero-width and formatting characters (`​`, `﻿`) survive `str.strip()`, so a visually blank name is creatable and passes the non-empty gate. The spec defines `normalize_name` as "trim; the single definition of trimmed", so the code is literally compliant — whether FR-6 wants Unicode normalization and internal-whitespace collapsing is a product decision, and 3.1 (which owns catalog UI) is the natural place to settle it. [addons/components/back/taiga_contrib_components/services.py:6-9]

- **Reorder reports success when it changed nothing.** `filter(project_id=..., id=...).update(order=...)` returns 0 for an unknown id, a foreign-project id, or a deleted component, and `BulkUpdateOrderMixin` still returns 204. The spec mandates the `project_id` predicate as the AC-2 guard and says to keep it, but it conflates "attacked" and "stale client" into the same silent success. Related: the payload is unbounded (one UPDATE per element, N sequential queries in one atomic block), concurrent reorders interleave with last-writer-wins, and a partial payload leaves the unnamed components tied at their previous `order` so the visible result differs from what the client sent. 3.1 builds the first real reorder payload and should decide whether a row-count check becomes a 400. [addons/components/back/taiga_contrib_components/services.py:22-26]

- **`ready()` is append-only, non-idempotent, and sensitive to `INSTALLED_APPS` order.** A second `django.setup()` in one process constructs a second `DefaultRouter` and appends a second `api/v1/` include. No `django.urls.clear_url_caches()` follows the append, so any app whose `ready()` runs earlier and resolves or reverses a URL materializes the pre-append resolver and the catalog routes 404 silently. `from taiga.urls import urlpatterns` also pulls Taiga's whole URLconf mid-`apps.populate()`, making boot success depend on the addon's position in `INSTALLED_APPS` — which nothing pins and nothing tests. The spec mandates this verbatim slack idiom and forbids the `try/except ImportError` that would mask a failure, so any change here is a deliberate divergence from the official pattern. [addons/components/back/taiga_contrib_components/apps.py:10-18]

- **`GET /api/v1/components` with no `?project=` returns interleaved rows from every visible project.** `filter_fields = ("project",)` makes the filter optional, so an omitted param yields the caller's whole cross-project catalog sorted by `(order, id)` and paginated at 30. No data leaks — `CanViewProjectFilterBackend` still applies — and official Taiga catalogs behave identically, so AC-2 holds. But it is a trap for any consumer that assumes the endpoint is project-scoped by construction. [addons/components/back/taiga_contrib_components/api.py:18]

- **The validator has an untested fail-open branch and two DRF-2 assumptions no offline test can settle.** When `attrs["project"]` is absent and `self.object` is `None`, `validate_name` returns having only trimmed — the uniqueness check is silently skipped and the DB index becomes a 500 rather than a 400. In practice the request already 400s on the missing required `project`, so there is no reachable bad outcome today, but it is an unconditional fail-open path with no test and no log line. Two related unknowns: whether `{"name": null}` is rejected by the vendored field layer (the addon's own guard returns early on `None`), and whether `taiga.base.exceptions.ValidationError` short-circuits `perform_validation` — if it does not, an update that both renames and illegally moves a component runs its uniqueness query against the foreign project and the error message names a project the caller may not be able to read. `ComponentValidator` is never instantiated in the suite (the stub `ModelValidator` is `class ModelValidator: pass`), so all three need a real Taiga stack. [addons/components/back/taiga_contrib_components/validators.py:15-26]

- **The stub's `__and__` returns `self`, silently neutering permission expressions.** Under the Layer B harness `IsAuthenticated() & HasProjectPerm("view_project")` evaluates to plain `IsAuthenticated()`. Nothing evaluates permissions behaviourally today, so nothing breaks — but the moment 2.3 adds a behavioural permission test to Layer B it will get confidently wrong answers with no warning. The shim exists to let imports resolve, not to answer questions about behaviour; that boundary needs restating before 2.3 leans on it. [tests/_taiga_stub/taiga/base/api/permissions.py:5-16, tests/_taiga_stub/taiga/permissions/permissions.py]

- **`bulk_update_perm = "change_component"` is a dead string that would fail closed on upgrade.** Taiga's project permissions come from a fixed `MEMBERS_PERMISSIONS` choice list and this addon registers nothing into it. 6.10.2's `BulkUpdateOrderMixin` never reads the attribute — the real gate is `bulk_update_order_perms` — so it is inert today, and the spec mandates setting it "to match official". But if a future Taiga version starts honouring it, an unregistered permission denies every request. Worth revisiting at the next `TAIGA_PIN` bump. [addons/components/back/taiga_contrib_components/api.py:20]

- **None of the five new modules uses a logger,** despite the ARCHITECTURE-SPINE Consistency Convention naming a `taiga_contrib_components` logger. Every silent-failure path above — zero-row reorder, skipped uniqueness check — is unobservable in production as a direct consequence. No AC covers it, so it was not in scope for 2.2. [addons/components/back/taiga_contrib_components/]

- **`test_addon_does_not_reference_taiga_stub` asserts a spelling, not a property.** `assert "_taiga_stub" not in _read(path)` is the substring-over-a-whole-file anti-pattern the 1.3 review banned in favour of parsed structure; it would not catch dynamic path manipulation that assembles the name. Low value to rewrite now, but it should not be cited as proof that production code cannot reach the shim. [tests/test_components_api.py:438]
